### 🔴 1. Admin cannot manual-create an AM or PM booking

**File**: `Pages/Admin/Index.cshtml.cs:146-149`

```csharp
[Required(ErrorMessage = "Requested time is required.")]
[RegularExpression(@"^\d{2}:\d{2}$", ErrorMessage = "Requested time must use HH:mm.")]
public string RequestedTime { get; set; } = string.Empty;
```

The `[RegularExpression]` on `ManualBookingInput.RequestedTime` rejects `"AM"` and `"PM"`. But the admin manual-create form dropdown (`Pages/Admin/Index.cshtml:80-86`) offers `<option value="AM">` and `<option value="PM">`, and `OnPostCreateAsync` itself has a branch that handles them (line 238-246). Validator runs first in `ValidateManualBookingInput()` and rejects, so admin selects "AM" → gets `"Requested time must use HH:mm."` every time.

My new `EditBookingInput` at `Pages/Admin/Index.cshtml.cs:501-503` uses `^(AM|PM|\d{2}:\d{2})$` and works correctly. The **create** path is the one broken.

**Impact**: every admin attempt at "Anytime AM/PM" manual booking fails with a confusing error. Admins likely work around by typing HH:mm.

**Fix**: change the regex on `ManualBookingInput.RequestedTime` to match `EditBookingInput`'s pattern.

### 🟠 2. Weekend bookings accepted; cancellation rules respect weekdays but creation doesn't

**File**: `Services/TimeRuleService.cs:33-51, 126-149`

`GetAllowedDateRangeUtcNow` computes `minDate` as "today +1 or +2" with no weekend skip. So Friday-afternoon-post-cutoff → `minDate = Sunday`. Users can book Saturday/Sunday. The work hours copy says "Monday to Friday, 7:30 a.m. to 4:00 p.m." but the DATE validator doesn't enforce it.

Meanwhile `IsCancellationAllowed` (line 137-141) DOES skip weekends when computing the cutoff day. So the two halves disagree: creation allows weekends, cancellation assumes weekdays.

**Impact**: a Sunday booking creation succeeds. Inspectors either work it, refuse it, or admin has to manually cancel.

**Fix**: skip Sat/Sun when computing `minDate` in `GetAllowedDateRangeUtcNow`, matching `IsCancellationAllowed`'s logic.

### 🟠 3. Case-sensitivity inconsistencies across public email handlers (Codex #5 confirmed)

**Files**: `Pages/Index.cshtml.cs:333, 387, 497, 519, 546, 577-579`

Email normalization is not consistent across the public handlers:

| Handler | Normalization |
|---|---|
| `OnPostLookupInspectionsAsync` line 333 | `.Trim().ToLowerInvariant()` |
| `OnPostCancelInspectionAsync` line 387 | `.Trim()` — **NOT lowercased** |
| `OnPostProjectEmailVerificationStatusAsync` 497 | `.Trim()` only |
| `OnPostSendProjectEmailCodeAsync` 519 | `.Trim()` only |
| `OnPostVerifyProjectEmailCodeAsync` 546 | `.Trim()` only |
| `OnPostSaveContactAjaxAsync` 577-579 | `.Trim()` only |

Downstream queries then do `b.ContactEmail == emailRaw` exact match. SQL Server's default `Latin1_General_CI_AS` collation is case-insensitive, so you don't hit this today. On a case-sensitive collation (migration, DB replacement, cloud DB change) mixed-case users silently lose their own bookings.

**Fix**: add `.ToLowerInvariant()` uniformly to every handler that takes email input. Admin `ManualBooking.ContactEmail` is saved as `.Trim()` only (`Admin/Index.cshtml.cs:234`) — also needs lowercasing, otherwise mixed-case admin entries have the same lookup problem.

### 🟠 4. Admin summary email goes to the `FromMailbox`, not `Email` (recipient) — inconsistent with initial booking email

**File**: `Pages/Admin/Summary.cshtml.cs:177-178`

```csharp
var fromMailbox = _notificationOptions.FromMailbox;
var toEmail = _notificationOptions.FromMailbox;   // ← sends to FROM, not the admin distribution list
```

`NotificationOptions` has two distinct recipient-ish fields: `FromMailbox` (Graph-authenticated sender, e.g., `reviews@korstructural.com`) and `Email` (admin notification recipient, e.g., `reviews@korstructural.com`). They happen to equal each other today in `appsettings.json`, so nobody notices. But `BookingService.SendInitialEmailsAsync` sends the admin NEW BOOKING email to `_notificationOptions.Email`. Summary email sends to `_notificationOptions.FromMailbox`. Two different notions used inconsistently.

**Fix**: summary should use `_notificationOptions.Email` (or whatever you rename that to) for the admin recipient. While you're in there: consider renaming `NotificationOptions.Email` to `AdminRecipientEmail` since it's ambiguous today.

### 🟡 5. Summary emails don't show project name or hyphenated phone — regressed vs. V1.1 #3a/#3b

**File**: `Pages/Admin/Summary.cshtml.cs:437, 433`

V1.1 #3a made booking emails show `30961-01 River District Parcel 29` via `FormatJobLine`. V1.1 #3b made phones show as `604-555-1234`. Neither applies to the Summary email (the morning roster sent to inspectors + admin):
- Job column renders `b.ProjectNumber` (Base5-only, e.g., `30961`)
- Contact column interpolates raw `b.ContactPhone` (no hyphens)

Inspectors still open the morning roster and see the old format even though every other email now shows the richer format.

**Fix**: pass `ProjectNumberDisplay`/`ProjectName` through `SummaryRow` (currently missing those fields) and use a `FormatJobLine`-equivalent. Format phone via `PhoneNormalizer.Format`. ~15-line change.

### 🟡 12. `/healthz` requires interactive OIDC auth, so no automated probe can reach it

**File**: `Program.cs:33-37, 202-204`

`HealthzAccess` policy = `RequireAuthenticatedUser`. The only auth scheme is `AddMicrosoftIdentityWebApp` (OIDC). A monitoring tool probing `/healthz` gets a 302 to Microsoft login and can't follow. Also `AddDbContextCheck` opens an EF connection per probe.

**Fix**: add a second auth scheme (API key / trusted probe subnet), scope `HealthzAccess` to accept either OIDC-authenticated or probe-authenticated. Replace `AddDbContextCheck` with `AddSqlServer(connectionString, healthQuery: "SELECT 1")` so probes don't churn EF.

### 🟡 19. Public OTP `ProjectBootstrapVerificationService.SendCodeAsync` has a small race on concurrent same-user sends

**File**: `Services/ProjectBootstrapVerificationService.cs:92-138`

Two simultaneous clicks of "Send Code" for (project, email): both call `FirstOrDefaultAsync` before either inserts. Both see null → both `.Add` → both `SaveChangesAsync`. Second hit throws on the unique index. User sees a 500 or retry error.

Low probability (user double-clicking). Could harden with upsert-with-retry on conflict.

**Fix**: wrap in a serializable transaction, or catch the `DbUpdateException` and convert to a successful "code sent" outcome.
