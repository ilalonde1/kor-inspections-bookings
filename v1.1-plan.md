## #2 — Autocomplete shows all sub-numbers under the `-01` name

**Files**:
- `Kor.Inspections.App/appsettings.json` (`Deltek:Sql_ProjectSearchByPrefix`)
- `Kor.Inspections.App/Services/DeltekProjectService.cs` (`SearchProjectsAsync` and `QueryProjects`)

**Problem**: Currently the search returns each WBS1 with its own `Name`. Griffin wants every sub-number (`30961-01`, `30961-02`, `30961-03`...) to display the `-01` row's name (e.g., "River District Parcel 29").

**Fix**:

1. Modify `Deltek:Sql_ProjectSearchByPrefix` in `appsettings.json` to LEFT JOIN to the `-01` row to fetch its `Name`. Schema confirmed: project header rows have `WBS2=''` and `WBS3=''`, so:
   ```sql
   SELECT TOP 20
       PR.WBS1 AS ProjectNumber,
       COALESCE(P01.Name, PR.Name) AS ProjectName
   FROM PR
   LEFT JOIN PR P01
       ON P01.WBS1 = LEFT(PR.WBS1, LEN(PR.WBS1) - CHARINDEX('-', REVERSE(PR.WBS1))) + '-01'
       AND COALESCE(P01.WBS2, '') = ''
       AND COALESCE(P01.WBS3, '') = ''
   WHERE COALESCE(PR.WBS2, '') = ''
       AND COALESCE(PR.WBS3, '') = ''
       AND (PR.WBS1 LIKE ? OR PR.Name LIKE ?)
   ORDER BY PR.WBS1
   ```
   Two notes on the JOIN expression:
   - `LEFT(PR.WBS1, LEN(PR.WBS1) - CHARINDEX('-', REVERSE(PR.WBS1)))` strips the trailing `-NN` suffix.
   - If a WBS1 has no hyphen (defensive), the join condition won't match and `COALESCE` falls back to `PR.Name`.
2. No C# code change should be required because `DeltekProjectService.QueryProjects` already reads `ProjectNumber` and `ProjectName` columns by name from the reader.
3. Verify the placeholder count: the new SQL still has exactly two `?` placeholders. `AddParametersForPlaceholders` handles two correctly.

**Acceptance**:
- `dotnet build` succeeds.
- Manual: search "30961" in the autocomplete with the dev DB → all WBS1 entries starting with `30961-` appear, each showing `River District Parcel 29` as the name.
- Manual: search a project number that exists only as a single sub-number → still shows correctly with its own name.
- Manual: search a project name (text search hits the `OR PR.Name LIKE ?` branch) → still works; the displayed name is the `-01` row's name.
- The 60s memory cache key `deltek:search:{maxResults}:{TERM}` already discriminates by term; no cache-key change needed.

**Risk**: medium.
- The SQL change is the only behavior change; if the join expression is wrong on a real Deltek DB, all autocomplete results will fall back to `PR.Name` (the `COALESCE` second arg) — i.e., **same behavior as today**. So the worst-case is "no improvement", not a regression.
- Watch out for SQL Server collation case-sensitivity if WBS1 values are stored mixed-case (the user's sample is uppercase, so likely fine).

**Open question for the user before commit**: is the 60s `deltek:search:` cache TTL too long while testing this? May want to bump down to 5s during the QA window.

## #4 — Edit Booking from admin dashboard

**Files**:
- `Kor.Inspections.App/Pages/Admin/Index.cshtml` (new form per row)
- `Kor.Inspections.App/Pages/Admin/Index.cshtml.cs` (new `OnPostEditAsync` handler + `EditBookingInput` class + helper)
- `Kor.Inspections.App/Services/BookingService.cs` (new `SendRescheduledEmailsAsync`)
- New test file `Kor.Inspections.Tests/Pages/AdminIndexModelEditBookingTests.cs`

**Problem**: Admins need to push an inspection to a different date/time. Currently the only options are Cancel + re-create.

**Fix** (high level — implement in this order):

1. **Backend handler** `OnPostEditAsync(Guid id, EditBookingInput edit)`:
   - Fetch booking; 404-equivalent (set `StatusMessage` and redirect) if missing.
   - Block if `Status` is `Cancelled` or `Completed`.
   - Validate `edit.RequestedDate` and `edit.RequestedTime` with the same logic as `OnPostCreateAsync`:
     - `GetMinimumManualBookingDate(edit.OverrideCutoff)` → `maxDate` window check.
     - `TimeOnly.TryParseExact` for HH:mm; allow `"AM"` / `"PM"` strings.
     - Compute `newStartUtc`, `newEndUtc` (60-minute slot, or 4-hour AM/PM block).
     - Re-run `_timeRules.GetAvailableSlotsForDate` and verify the new slot is open. **EXCLUDE the booking being edited** from the existing-bookings list so it doesn't conflict with itself.
   - Capture `oldStartUtc`, `oldEndUtc`, `oldTimePreference`.
   - Update booking: `StartUtc`, `EndUtc`, `TimePreference`. **Null out `RouteOrder`** (the old order is meaningless on a new day).
   - Add `BookingAction` with `ActionType = "Edited"`, `PerformedBy = User.Identity?.Name`, `Notes = $"From {oldStartUtc:yyyy-MM-dd HH:mm}Z to {newStartUtc:yyyy-MM-dd HH:mm}Z"`.
   - Same `DbUpdateConcurrencyException` handling as Assign/Cancel.
   - On success, call `_bookingService.SendRescheduledEmailsAsync(booking, oldStartUtc, oldEndUtc, oldTimePreference)`.
   - Redirect with the standard query params preserved.
   - Skip the email + DB write entirely if `newStartUtc == oldStartUtc && newEndUtc == oldEndUtc && newTimePreference == oldTimePreference` — set `StatusMessage = "No changes made."` and redirect.

2. **`EditBookingInput`**: nested class on `IndexModel` with `RequestedDate`, `RequestedTime`, `OverrideCutoff`. Same `[Required]` and `[RegularExpression]` annotations as `ManualBookingInput`'s date/time fields.

3. **UI** in `Admin/Index.cshtml`: in the actions cell, add an `<details>` (collapsed by default) labelled "Edit Booking". Inside, a form with date input, time select (populated with the same `Model.AvailableManualTimes` plus AM/PM), cutoff override checkbox, and Save button. Style consistently with the existing assign/cancel forms. The form posts to `?handler=Edit&id=@b.BookingId`.

4. **Email** `BookingService.SendRescheduledEmailsAsync`:
   - Mirror `SendCancellationEmailsAsync`'s structure (try/catch around send; never throw).
   - Subject: `Field Review Rescheduled - {ProjectNumber} - {newStartLocal:yyyy-MM-dd HH:mm}`.
   - Body uses a new `BuildRescheduledEmailHtml(booking, oldStartLocal, oldEndLocal, newStartLocal, newEndLocal, manageUrl, isInspector)`:
     - Lead sentence: "Your field review has been rescheduled." (or for inspector: "A field review you are assigned to has been rescheduled.")
     - Two-row table: "Previous date/time" → old; "New date/time" → new (use `BookingDisplayHelper.GetTimeDisplay`).
     - Standard Job # / Address / Comments rows.
     - Manage link (clients only).
     - Office contact note.
   - Send to `booking.ContactEmail` always; send to inspector via `GetAssignedInspectorAsync(booking.AssignedTo, requireEnabled: false)` if assigned.

5. **Tests** in `AdminIndexModelEditBookingTests.cs` (LocalDB fixture, mirror existing patterns):
   - Happy path: edit Unassigned booking → status updated, action recorded with old → new note, email mock invoked.
   - No-change path: post the same date/time → no DB write, no email, `StatusMessage = "No changes made."`.
   - Cancelled booking: cannot be edited → status message + redirect, no DB write.
   - Completed booking: cannot be edited.
   - Slot taken: target slot already has `MaxBookingsPerSlot` overlapping → `BookingSlotUnavailableException` mapped to `ModelState` error, no DB write.
   - Self-conflict: editing a booking to the slot it currently occupies must succeed (the "exclude self" filter works).
   - Concurrency: stale context → `DbUpdateConcurrencyException` → "modified by another user" status message, no email.
   - Cutoff override: editing to "tomorrow after 2 PM" without override fails; with override succeeds.

**Acceptance**:
- All new tests pass; existing test suite passes.
- `dotnet build` succeeds.
- Manual: in dev, edit a booking → date/time updates, contact gets the rescheduled email, `BookingAction` row records the old → new transition.
- Manual: try to edit a Cancelled booking → blocked with friendly message.
- Manual: edit a booking that has an assigned inspector → both client and inspector receive emails.
- The unique index `IX_Bookings_NoDuplicateActiveSlot` (project + email + StartUtc, status≠Cancelled) catches the case where editing would create a duplicate active slot for the same email — the resulting `DbUpdateException` should be mapped to a friendly status message ("Cannot reschedule to a slot you already have a booking for"). Add a test for this.

**Risk**: medium-high. Largest blast radius of the four. New handler, new email, new UI form, new test class. Land in its own PR; do not bundle with #1-3.
